# CLAUDE.md

## Project

`auto_accompaniment` is a real-time assisted jazz accompaniment system for a semi-automatic acoustic accordion.

The accordion plays the incoming melody acoustically via solenoids. A separate accompaniment engine generates piano accompaniment and sends MIDI to a Yamaha MU80, which is heard through a speaker.

Primary target board: **Arduino UNO Q 2GB**.

Before making implementation changes, read:

1. `README.md`
2. `docs/CONCEPT_REVIEW.md`
3. `docs/DEVELOPMENT_SPEC.md`

Reference project for selected musical ideas:

- https://github.com/hasebems/Loopian_Rust

Do not assume the whole Loopian architecture should be copied. Only selected algorithms/concepts are relevant.

## Core product concept

The goal is not a backing-track player.

The desired behavior is closer to a familiar jazz pianist accompanying a melody player:

- listen to / inspect the melody
- know the song/chord context
- leave space when melody is busy
- fill during long notes or rests
- react to phrase direction and upcoming target notes
- respond to live touch-bar gestures
- produce musically constrained improvisation

The touch bar is not primarily a conventional keyboard. It is an expressive intent/contour controller.

Examples:

- tap -> comping/chord response
- slow slide -> arpeggio
- fast slide -> run/fill
- slide right -> prefer upward melodic motion
- slide left -> prefer downward melodic motion

## Critical timing concept

Incoming melody MIDI is intentionally delayed by a configurable look-ahead interval.

```text
scheduled_accordion_time = BLE_receive_time + LOOKAHEAD_MS
```

Initial test values:

```text
0, 300, 500, 1000 ms
```

This is not needed for computation time. It gives the accompaniment engine visibility into upcoming melody events.

Touch gestures are different. They are generated by a human reacting to what is audible now. Do not blindly add `LOOKAHEAD_MS` to touch input.

When a touch event occurs, the engine can use the already buffered upcoming melody to generate an immediate or musically quantized response.

This timing model must be validated experimentally.

## Responsibility guidance

### Linux / QRB2210

Prefer Linux for:

- BLE MIDI reception
- melody buffer
- tempo/beat/song state
- melody analysis
- Jazz Engine
- touch + melody integration
- accompaniment MIDI event generation
- configuration/logging/debugging

### STM32U585

Prefer MCU for:

- deterministic actuator scheduling
- solenoid I/O
- hard maximum solenoid ON time
- touch sensor sampling
- gesture preprocessing
- watchdog/panic/all-off
- optionally scheduled physical DIN MIDI output

Do not make solenoid safety dependent on a healthy Linux process.

## Jazz Engine principles

Start rule-based. Do not introduce an LLM or generative AI model for the MVP.

Priority musical mechanisms:

1. chord/scale-aware pitch snapping
2. direction preservation during slides
3. repeated-note avoidance during continuous movement
4. chord extensions (7/9/11/13) controlled by style/jazz degree
5. melody-density-aware comping
6. long-note/rest-aware fills
7. future target-note-aware runs
8. small velocity/timing humanization

Randomness should choose among valid musical alternatives, not replace harmonic logic.

## Development approach

Do not attempt the full hardware system at once.

Preferred order:

1. Host-side simulation
2. UNO Q BLE MIDI receive/logging
3. Timestamped fixed-delay melody relay
4. STM32 deterministic solenoid scheduler
5. Touch bar prototype
6. Live Jazz Engine
7. MU80 output
8. Timing/jitter measurement
9. Musical tuning

Each milestone should have a testable acceptance criterion.

---

## Code quality

- Separate musical logic from hardware I/O
- Keep Jazz Engine deterministic under a fixed random seed for testing
- Use monotonic time for scheduling
- Make event queues bounded and observable
- Log actual vs requested execution timestamps
- Unit-test pitch snapping, direction rules and quantization
- Replay recorded MIDI/touch sessions for regression tests
- Prefer explicit state machines over hidden timing behavior
- Avoid blocking calls in real-time paths
- Ensure Note Off / All Notes Off behavior is tested
- Ensure all-solenoids-off works independently of Linux

---

## Do not prematurely optimize

For the MVP, prioritize audibility and musical feel over architectural perfection.

A simple 24-segment touch bar and piano-only MU80 output are acceptable.

Do not add bass, drums, AI models, complex GUI, networking, or continuous-position sensor hardware until the central interaction has been demonstrated:

**accordion melody + touch gesture -> coherent live piano response.**
